# 双 AI 协作开发方法论（豆包甲方 + WorkBuddy 乙方）

> 本文是整套方法的完整说明。SKILL.md 是执行入口，本文是原理与决策依据。
> 先读 SKILL.md 跑通流程，遇到"为什么这么做/该不该这么做"再回来查本文。

## 0. 这套方法的本质

**一句话**：两个 AI（豆包 ⇄ WorkBuddy）通过 git + 文件信箱协作完成软件开发，一方派活/审核、另一方干活/改错，以"提交 → 审核 → 意见 → 修改"的循环往复逼近满意，全程自动、可追溯、可回滚。**角色可互换**：不限于豆包指挥 WorkBuddy，也可以是 WorkBuddy 让豆包干活。

**为什么有效**：
1. **角色分离**——干活的和验收的分开，杜绝"自己写自己审"的盲区
2. **介质是 git**——一切产出可追溯（commit hash）、可回滚（git revert）、可比对（git diff）
3. **信箱是文件**——意见落盘（inbox/review_roundN.md），双方按约定读取，无需人工搬运
4. **循环有收敛标准**——"连续两轮无 P0"即可收工，不无限空转

## 1. 前置准备清单（做之前要做什么）

开工前逐项确认，缺一项都可能在中途卡壳：

### 1.1 环境探测（一次性的）
| 项 | 怎么做 | 确认标准 |
|---|---|---|
| WorkBuddy 桌面版在运行且已登录 | 看任务栏/进程 | 能正常对话即可 |
| headless CLI 入口存在 | 探测 `resources/app.asar.unpacked/cli/dist/codebuddy-headless.js` | 文件存在（约 11MB） |
| Node 可用 | `node --version` | 有版本号 |
| token 可提取 | `python dispatch.py --status` | 打印 "token: 有效" |
| serve 可启动 | `python dispatch.py --status` | 打印 "serve: 运行中/未运行"（未运行也 OK，派活时会自动拉起） |

CLI 入口探测命令（PowerShell）：
```powershell
Get-ChildItem "E:\LenovoSoftstore\Install\WorkBuddy\resources\app.asar.unpacked\cli\dist" -Filter "codebuddy-headless.js"
# 找不到时全盘搜：Get-ChildItem -Path C:\,E:\ -Recurse -Filter codebuddy-headless.js -ErrorAction SilentlyContinue 2>$null
```

### 1.2 项目初始化
1. **建 git 仓库**：`git init`（必须——通信协议依赖 commit）
2. **配 git 身份**（仓库级即可，避免全局污染）：
   ```
   git config user.name "workbuddy-agent"
   git config user.email "agent@local"
   ```
3. **写 .gitignore**：至少忽略 `.cache/`、`_*.out`、`__pycache__/`、测试临时产物
4. **建 inbox 目录**：`inbox/`（通信信箱，见 §2.2）

### 1.3 需求文档（双方共同基线）
- **PRD.md**：产品需求（功能、边界、优先级、交互）。乙方按此实现，甲方按此验收
- **CHECKLIST.md**：逐条可打勾的验收清单（建议分 A~K 组：核心功能、交互、存储、异常、工程等）
- 这两份文件是**双方契约**：乙方照着做，甲方照着审。写好后再开工

### 1.4 部署派活桥
- 复制 `scripts/dispatch.py` 到项目根目录
- 首次派活自动完成：提 token → 起 serve → 派任务 → 读结果
- 换机/换项目时用环境变量覆盖默认路径（见脚本头注释）

### 1.5 定时审核任务（可选，推荐）
创建每小时定时任务，内容模板见 §4.4。注意：定时任务创建有最短间隔限制（1 小时），且需按定时任务 Skill 规范创建。

### 1.6 环境依赖（针对目标项目）
- 乙方写代码时要求自测（如 `python -m py_compile`）
- 甲方审核时也要能跑（装依赖：`pip install -r requirements.txt`）
- 明确哪些测试项自动化能跑、哪些必须人工（如真实鼠标划词、朗读出声）

## 2. 角色与通信协议

### 2.1 角色分工（角色可互换）
| 角色 | 职责 | 权限 |
|---|---|---|
| 审核方 | 派活、审核、写意见、判定收敛 | **只审不改**（调试性只读验证除外） |
| 干活方 | 实现、修改、跑测试、commit | 改代码、跑命令、提交 |

**角色互换规则**（谁当审核方、谁当干活方，按任务性质定）：
- **豆包当审核方（模式 A，最常用）**：代码开发类任务——豆包审核更严、验收标准更可执行
- **WorkBuddy 当审核方/派活方（模式 B）**：WorkBuddy 在自己的工作流中遇到需要豆包能力的事（审核意见、查资料、润色文案、翻译、写文档、出方案），把任务写成任务单放进 inbox/tasks/，豆包处理完写回 inbox/results/
- 判断标准：**谁对验收标准最有把握，谁当审核方**；另一方干活。两边各擅其长时可以轮换。

**铁律（与方向无关）**：审核方绝不直接改代码；干活方无权改 PRD.md、CHECKLIST.md、审核基线。

### 2.2 文件信箱约定（inbox/）
| 文件 | 谁写 | 内容 |
|---|---|---|
| `inbox/review_roundN.md` | 审核方 | 第 N 轮审核意见（N 递增） |
| `inbox/last_reviewed_commit.txt` | 审核方 | 最近已审核的 commit hash（基线） |
| `inbox/tasks/NNN_*.md` | 派活方（模式 B） | 任务单（NNN 三位序号递增） |
| `inbox/results/NNN_*.md` | 干活方（模式 B） | 结果单（NNN 与任务单一致） |
| `inbox/last_task_processed.txt` | 干活方（模式 B） | 已处理到的任务序号（防重复） |
| `inbox/audit_heartbeat.txt` | 定时任务 | 心跳留痕（每次追加时间） |
| `inbox/worker_alive.txt` | 干活方 | 干活方心跳（可单行覆盖） |

### 2.3 git 通信协议
- **乙方完成一段工作 → 必须 git commit**（提交信息写清做了什么）
- **甲方审核 → 对比基线**：`git rev-parse HEAD` vs `last_reviewed_commit.txt`，不同 = 有新活
- **审核通过 → 更新基线**为当前 HEAD

## 3. 执行流程（一轮完整的闭环）

```
模式 A：豆包派活 → WorkBuddy 干活并 commit → 豆包审核 → 写 review_roundN.md → 派修 → 再审 → 连续两轮无 P0 → 收敛
模式 B：WorkBuddy 写任务单到 inbox/tasks/ → 豆包轮询处理 → 写结果到 inbox/results/ → WorkBuddy 读取
```

### 3.1 模式 A 派活（豆包 → dispatch.py）
任务文本要包含（缺一不可）：
1. **明确 cwd**（如 D:\xxx\project）
2. **要做什么**（写哪些文件/改哪个 bug）
3. **验收要求**（必须 py_compile 通过、必须 commit、提交信息写什么）
4. **边界**（不要动什么文件、不要做额外的事）
5. **（可选）模型**：默认 `glm-5.3`；想换模型就在任务文本开头写 `[model=<id>]`（如 `[model=kimi-k3-1]`），或 `--model <id>` 参数。模型清单见 setup.md §9。
6. **（GUI/核心逻辑必带）自带自测**：要求乙方写完模块**附带 selftest/最小自测**（关键函数断言、边界输入、异常输入各至少 1 条），任务文本写明"写完先跑自测确认通过再 commit"——审核时直接跑，不再只靠 py_compile

模板：
```
python dispatch.py "在 <cwd> 目录：<具体任务>。要求：1) <功能点>；2) 附带 selftest（关键函数+边界+异常各至少1条），写完先跑自测通过；3) python -m py_compile <文件> 确认语法；4) git add 并 commit，提交信息 '<commit信息>'。不要修改 <禁区文件>。" --timeout 300
```

**批量派活（--queue）**：任务较多时写个队列文件（每行一个任务，可带 `[model=xxx]` 标记，`#` 开头为注释），
`python dispatch.py --queue tasks.txt` 逐个派发执行，适合"多个独立小模块/多文件独立任务"。

**run 状态跟踪（--list-runs）**：每次派活自动记录到 `.cache/runs.json`；
`python dispatch.py --list-runs [--limit N] [--check]` 可查历史与每个 run 是否仍在执行（active/completed）。

### 3.2 审核（审核方）
1. 读干活方所有产出文件（不要只看 diff 摘要）
2. 对照 CHECKLIST.md 逐条打勾
3. 跑自动化验证：py_compile、**selftest/单元测试（派活时要求乙方自带的自测，直接跑）**、关键路径实测
4. 问题分三级：
   - **P0（阻塞）**：功能错误、崩溃、数据损坏、需求核心不满足——必须改
   - **P1（该改）**：明显缺陷、体验问题、约定违反——应该改
   - **P2（建议）**：优化项、风格、边界增强——可选
5. **5 维评分**（review_round 模板已内置评分表，每题 1-5 分，依据写一句话证据）：
   - **正确性**：功能符合 PRD，无错误结果
   - **可维护性**：模块化、命名、注释、无重复代码
   - **性能**：响应速度、资源占用、高频场景不卡
   - **安全**：剪贴板/数据/路径/异常不外泄不破坏（对应 CHECKLIST J/K 组）
   - **界面**（GUI 类）：布局、美化、按钮统一、字体无遮挡、DPI（对应 L 组）
   - 总分 **<20/25 = 未达收敛线**，即使无 P0 也应提示改进方向
6. 写 review_roundN.md：总体结论 + **评分表** + 逐条问题（现象/根因/修改方向）+ 验收标准 + STATUS

### 3.3 模式 A 派修（豆包）
- 把 review_roundN.md 的存在和要点告诉干活方：`请阅读 <cwd>/inbox/review_roundN.md 并按意见修改`
- 要求干活方：改完 → py_compile → commit → 汇报 hash

### 3.4 模式 B 任务队列（WorkBuddy → 豆包）

**任务单**（派活方写，模板 task_request.template.md）：
```
inbox/tasks/001_<简述>.md     # NNN 三位序号，递增
```
内容：需求描述 / 验收标准 / 参考文件 / 注意事项（禁区）。

**处理方流程**（豆包）：
1. 轮询：`python poll_tasks.py` → 列出序号大于 last_task_processed.txt 的任务
2. 逐任务处理：读任务单 → 执行（写代码/审核/查资料/润色/翻译等）→ 写结果单
3. 结果单：`inbox/results/001_<同简述>.md`（NNN 必须与任务单一致，模板 task_result.template.md）
4. 标记：`python poll_tasks.py --mark 001`（更新 last_task_processed.txt，防重复处理）

**触发方式**：
- 按需：用户说"看下任务队列" → 处理
- 定时：每小时 cron（query 模板 B，见 4.x）自动轮询处理并汇报
- 派活方（WorkBuddy）侧：由用户把它引到约定——任务写 inbox/tasks/、结果读 inbox/results/

### 3.5 收敛判断
- 本轮无 P0 → review 末尾写 `STATUS: NO_P0`
- **连续两轮 NO_P0 → 宣布收敛**，交付用户过目
- **加分条件（建议）**：收敛轮总分 ≥20/25；总分 <20 且无 P0 → 在 review 备注里列出改进方向（不算阻塞，但建议修到 20+）
- 有 P0 → 继续派修循环（每轮 N+1）

### 3.6 双审 / 交叉审核（关键模块必做，普通模块可选）
**为什么**：单一审核方有盲区（自己写自己审更严重）；两个审核方交叉看，能发现单审发现不了的问题（复测实证：不同模型盲区不同，交叉审核显著提高质量）。

**适用对象**：关键模块（核心算法/数据处理/支付/安全/首次交付/跨模块集成）。
**做法**（两种任选）：
1. **独立双审**：主审先审（不看对方结论）→ 复审独立再审 → 汇合；意见冲突时按"更严的一方 + 证据"裁定，仍僵持则问用户
2. **抽查复核**：复审只抽查主审结论的 30%（读主审 P0/P1 对应的代码）→ 确认无漏审

**谁来当复审**（按可用性任选）：
- 另一个模型实例（派活换 `[model=xxx]` 让不同模型看同一份代码，最能暴露盲区）
- WorkBuddy（模式 B：把"审 review_roundN 主审结论"写成任务单放 inbox/tasks/，豆包处理）
- 用户本人（关键决策保留人工复核权——参考 humanize 模式：人类始终保留最终架构决策权）

**记录**：review_roundN.md 的"复审"段填：复审方 / 方式 / 结论（同意 / 补充问题 / 分歧点+裁定）。

## 4. 定时自动审核（可选但推荐）

### 4.1 建任务
- cron 每小时整点：`0 * * * *`
- query 必须包含：心跳留痕 → 查 commit → 对比基线 → 有新提交则审核并写 review_roundN → 更新基线 → 向用户汇报（**禁止静默**，用户明确要求每小时必须收到运行状态消息）

### 4.2 心跳的意义
- 用户随时能打开 `inbox/audit_heartbeat.txt` 确认任务在跑
- 没心跳 = 任务挂了/没触发，立即排查

### 4.3 汇报格式（简洁，2-3 行）
```
本轮心跳触发时间：<时间>
无新提交：WorkBuddy 未动，任务正常运行，下次检查：<下一整点>
或：新 commit <hash>，P0 x 个 / P1 y 个 / P2 z 个
```

### 4.4 定时任务 query 模板（核心规则）

**模板 A（自动审核，模式 A 用）**——完整可复制版见 `assets/templates/cron_query.template.md`：
```
0. 心跳留痕：追加当前时间到 <cwd>/inbox/audit_heartbeat.txt
1. 查 git rev-parse HEAD
2. 读 <cwd>/inbox/last_reviewed_commit.txt 对比：相同则无新提交直接汇报退出
3. 有新提交：读产出文件 + 对照 CHECKLIST + 跑验证（py_compile/selftest）
4. 问题分 P0/P1/P2，写 review_roundN.md，更新基线
5. 收敛判断：连续两轮 NO_P0 则告知用户可过目
6. 强制汇报：无论有无新提交，必须向用户发运行状态消息，禁止静默
```

**模板 B（自动轮询任务队列，模式 B 用）**：
```
0. 心跳留痕：追加当前时间到 <cwd>/inbox/audit_heartbeat.txt
1. 执行 python poll_tasks.py 检查 <cwd>/inbox/tasks/ 有无新任务
2. 无新任务 → 进入第 5 步
3. 有新任务：逐个处理（读任务单 → 执行 → 写结果到 inbox/results/NNN_*.md → 更新 last_task_processed.txt）
4. 汇报处理了哪些任务、结果如何
5. 强制汇报：心跳时间 / 有无新任务 / 处理情况。禁止静默。
```

## 5. 注意什么（风险与红线）

### 5.1 并发冲突（最常见的坑）
- **桌面版 WorkBuddy 和 CLI 派活是两套独立会话**，同时改同一仓库会互相踩
- 规则：**桌面板活跃时，CLI 别碰同一工作区**；反之亦然
- 处理办法：先看乙方心跳/最近文件改动时间判断活跃性；需要并行时用**独立沙盒仓库**（如 demo/ 子目录独立 git init）

### 5.2 权限模式
- serve 必须带 `--permission-mode auto`，否则 `git commit` 等操作卡在权限确认（无人确认 → 任务挂起）
- auto 是全局开关，agent 能执行大部分命令——**绑定 127.0.0.1 + 只给可信任务文本**，别派无关操作

### 5.3 token 安全
- token 从 WorkBuddy 进程内存提取（桌面版运行且已登录才有）
- 缓存于 `.cache/wb_token.txt`（已 gitignore，**绝不入库、绝不外发**）
- 有效期约 28 天，过期后重新提取（重开/重登 WorkBuddy 即刷新）
- 环境变量名是 `CODEBUDDY_AUTH_TOKEN`（不是 CODEBUDDY_API_KEY）

### 5.4 审核边界
- 审核方只审不改（干活方在等意见，别越俎代庖）
- 不改 PRD.md / CHECKLIST.md（契约文件，改动需用户确认）
- 验收标准必须在 review 里写清楚，让干活方"照着改就能过"
- 模式 B 下豆包是干活方：按任务单验收标准执行，超范围的事先问来源方

### 5.5 环境依赖
- selftest/集成测试可能因本机缺库报失败——**先区分"代码缺陷"和"环境缺失"**（如 requests 没装 vs 逻辑 bug），别把环境问题当 P0

### 5.6 派活文本质量（决定乙方产出质量）
- 指令要具体到"写什么、写到哪、怎么验收"
- 一次性给全要求，别让乙方猜
- 明确禁区（哪些文件不能动）

### 5.7 什么任务适合/不适合这套闭环
**适合**：写代码、改 bug、补测试、重构、格式化、提交归档、跑验证
**不适合**：需要真实 GUI 交互的验收（真鼠标划词、听声音）、涉及外部账号/支付/危险命令、需要人工判断的产品决策

### 5.8 定时任务维护
- 更新定时任务前先 get 当前配置再合并（Skill 规范）
- 用户要求每小时汇报 → 必须汇报，禁止静默（这是用户明确的强需求）

### 5.9 干活方可能漏 commit（复测实证）
- 即使任务文本明确要求 commit，agent 也可能写完代码不 commit 就收尾（D2W 复测：csv_summary.py 产出后仓库无 commit）
- 审核方**第一检查项**必须是 `git log --oneline -3` 验证 commit 存在，不要只依赖基线对比
- 首次审核（无基线）尤其要主动查；漏 commit 记为 P1"未完成 commit"，派修补上

### 5.10 环境代理会劫持 loopback（复测实证，易误判为"派活桥坏了"）
- 本机若设了 `HTTP_PROXY`/`HTTPS_PROXY`（含 WorkBuddy 自带代理），Python `urllib` 默认会把
  连 `127.0.0.1` 的请求也发给代理 → 502 Bad Gateway，且旧 `port_busy()` 会把 502 误判为"服务在跑"
- **判断依据**：`--status` 说运行中，但一派活就 502；或 `netstat` 里没进程却返回 502
- 脚本已修：loopback 请求统一空 ProxyHandler 直连；502/503/504 不再算"存活"
- 教训：**任何"本机服务探测"都要先绕开代理**，否则会被环境静默污染

### 5.11 新版 CLI 的 `--auth none` 已失效（复测实证）
- CLI v2.156+ 起 `--auth none` 会被 settings/内建默认覆盖，实际仍走 password 模式 → 派活 401
- 判据：serve 启动日志出现 `Auth enabled (mode: password)`
- 修正：启动 serve 时注入环境变量 `CODEBUDDY_GATEWAY_AUTH=none`（优先级最高），日志转为
  `⚠ Authentication is DISABLED.` 才算真关掉；脚本已内置
- 教训：**CLI 开关随版本会退化**，升级 WorkBuddy 后要复跑一次"最小派活冒烟"验证闭环

### 5.12 队列游标语义（模式 B 复测实证）
- 旧实现"单个最大序号当游标"在乱序处理时会静默吞掉中间任务
- 现改为"已处理序号集合"，`--mark N` 只记 N；兼容旧的单数字基线文件
- 迁移旧项目时注意：老文件里写 `5` 在新语义下只代表任务 5 已处理，需按需改成 `1,2,3,4,5`

### 5.13 冒烟自检清单（每次升级 WorkBuddy / 换机后跑一遍）
1. `python scripts/dispatch.py --status` → `token: 有效` 且 serve 状态真实
2. 派一个最小任务（建一个文件 + commit），确认产物与 commit 都真实出现
3. 三项都过 → 闭环可用；任一失败 → 先查 troubleshooting §14/§15

### 5.14 SSE 中断与"写一半没 commit"（分模块派活，实施项目必看）
- **实测踩坑**：一次派"写 core 引擎 + ui 框架"两个大文件，agent 写了一半 SSE 断了，且没 commit → 进度全丢，只能重派
- **规则**：
  1. **一次只派 1～2 个文件**，按 core → ui → 测试 → 集成逐模块推进，别贪多
  2. 任务文本**必须要求每写完一个模块立即 commit**（提交信息写模块名），禁止攒到结尾一起交
  3. 断点续跑：先 `git log --oneline` 确认已提交到哪个模块，再派"继续写下一个模块 XX，从上次 commit 之后继续，不要重写已提交部分"
  4. 验收也按模块来：每模块 py_compile + 对应功能实测，不等全写完
- **本质**：SSE 是流式连接，随时可能断；commit 是唯一可靠的断点。宁可多几个 commit，不能赌一次跑完

### 5.15 CLI/API 通道与桌面积分（实测观察，2026-10-12）
- **实测**：走 headless CLI + 本地 HTTP 端口派活（含完整写文件 + commit），WorkBuddy 桌面端积分明细**无任何消耗记录**（两次独立测试确认）
- **解释**（观察，非官方承诺）：桌面端积分只统计 UI 会话；CLI 通道使用本地会话 token，服务端口径与桌面积分显示分离
- **风险红线**：
  1. 这是"当前观察到的行为"，腾讯随时可能调整计费口径，**不要把它当永久免费**
  2. 通道依赖桌面版**运行且已登录**（token 从内存提取，约 28 天过期），桌面版关闭即断
  3. **个人小项目自用没问题；禁止规模化滥用**（批量刷任务当免费算力），服务端仍有速率/配额限制可能，且处于灰色地带
- 用之前提醒用户：能用、别依赖、别滥用

### 5.16 界面质量是硬验收项（GUI 任务，2026-10-12）
- **教训**：QuickTrans round5 实测 U-1（弹窗 DPI 位置跑偏）、U-2（译文残缺）——界面类 bug **光看代码发现不了，必须运行 + 目检**
- **规则**：
  1. **派活文本必须附界面硬性要求**（布局/美化/按钮统一/字体无遮挡/DPI 适配），直接抄 SKILL.md 对应小节
  2. **CHECKLIST 用 L 组（界面质量 GUI 必检）** 逐条打勾：L1 尺寸适配不溢出、L2 按钮统一、L3 布局合理、L4 字体不截断不重叠、L5 高 DPI 不跑偏、L6 配色层次、L7 交互反馈、L8 缩放不遮挡
  3. **审核必跑**：真实启动程序 + 截图目检，别只看代码/diff
  4. **分级**：文字被遮挡 / 按钮错位 / 显示不全 = **P0**（阻塞）；配色、间距不统一 = P1/P2
- **高频坑**（审核重点看）：高 DPI 缩放（125%/150% 屏）、中文长文本换行截断、窗口尺寸写死、系统字体缺失回退

### 5.17 一站式交付（开发收敛后必做，2026-10-12）
**收敛 ≠ 交付**。连续两轮 NO_P0 只说明代码过关；用户要的是"拿到就能用的成品"。五步：

1. **打包 EXE**（派活，模板见 SKILL.md §5.1）：PyInstaller 必带 `--onefile --noconsole --icon <图标> --clean`；
   隐式依赖（动态 import / 数据文件）加 `--hidden-import` / `--add-data`，打包失败查 troubleshooting §18
2. **安装程序**（可选但推荐）：Inno Setup 脚本（应用名/版本/安装目录/快捷方式/开始菜单/卸载/中文不乱码），产物 `<产品>_Setup.exe`
3. **产品使用手册**（派活，模板 USER_MANUAL.template.md）：简介/运行环境/安装/逐功能操作/快捷键/FAQ/截图
4. **交付验收**（审核方必做）：真实环境跑**打包后 EXE** 的关键路径（不是源码）；杀软不误报；
   版本号与 CHANGELOG 一致；**L 组界面质量在成品上复检**（打包后字体/布局可能变化——资源未打进包是高频原因）
5. **归档交付**：写 DOD.md（交付物清单：EXE/安装包/手册/源码 commit hash + 验证方式/结果 + 已知缺口）；
   最终 commit 归档；交付用户时一次性给：产物路径 + 验证方式 + 已知缺口

**产物位置约定**：源码在项目根，打包产物统一 `dist/`，手册 `USER_MANUAL.md`，交付单 `DOD.md`。

### 5.18 需求中途变更管理（2026-10-12）
**症状**：开发到一半用户加功能，若直接"口头加需求"派活 → 乙方做偏、CHECKLIST 对不上、验收扯皮
**规则**：
1. 中途变更**先走契约**：豆包起草 PRD.md / CHECKLIST.md 增量更新 → **用户确认** → 再派活（契约文件改动必须用户确认，这条铁律不因变更而松动）
2. 变更下发时明确"在现有基础上改，不动已验收部分"（配合 git 基线，乙方 diff 后修改）
3. CHECKLIST 新条目单独编号（如 B6、C5），审核时只对新增/受影响项复核，已验收项不重审
4. 变更影响面大（涉及核心架构）→ 按分模块派活重新切分，别一次塞给乙方

### 5.19 多项目并发（1.4.0 新增）
**场景**：同时跑两个项目（如 A 项目在写、B 项目在改），或桌面版与 CLI 并行时互不干扰。
**规则**：
1. **同 serve 多 cwd 已支持**：run 的 cwd 由任务文本指定，serve 不必每项目一个；只要桌面版不碰同一仓库即可
2. **重度并行 → 独立端口**：每个项目用独立 serve 端口与缓存：
   ```
   $env:WB_PORT = "51742"; $env:WB_PROJECT = "D:\B项目"; $env:WB_CACHE = "D:\B项目\.cache"
   python dispatch.py "..." 
   ```
   serve.pid / serve.log 已按端口隔离（serve.pid_51742），`--stop` 只停对应端口
3. **token 共用**：token 缓存在各项目 .cache 下，可共用（复制 wb_token.txt 或设 WB_CACHE 指向同一缓存目录）；token 有效期约 28 天
4. **仍守 §5.1**：桌面版与 CLI 不能同时改同一仓库

### 5.20 派活队列与 run 跟踪（1.4.0 新增）
- **--queue tasks.txt**：每行一个任务（可带 `[model=xxx]`，`#` 注释），逐个派发。适合多个独立小任务；任务间有依赖的先排好序或分开派
- **--list-runs [--limit N] [--check]**：查派活历史（时间/cwd/模型/摘要）；`--check` 逐个查 run 活跃状态（active=执行中 / completed=已完成 / http_N=查询失败）
- **用途**：跑完一批任务后 `--list-runs --check` 确认全部 completed；发现 active 残留（SSE 断了但 agent 还在跑）→ 等它自然结束或按 §17 续跑
- **记录位置**：`.cache/runs.json`（最多留 200 条，已 gitignore）
